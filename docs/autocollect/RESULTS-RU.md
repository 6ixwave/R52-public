# Автосбор R-52 2.12

Запустите R52.cmd. В «Автосборе» по умолчанию включён «Широкий поиск без ввода запросов». Система последовательно использует 16 тематик на каждом включённом источнике. Дополнительные ручные запросы доступны в «Новой цели». Текстовая категория передаётся существующему поисковому методу сборщика. Принятые товары включённых источников также периодически обновляются.

Планировщик впервые ставит задачу примерно через 15 секунд, затем раз в минуту проверяет сроки. По умолчанию поиск выполняется раз в час, обновление карточки раз в 6 часов, максимум 20 новых предложений за цикл. Для каждой цели задаётся собственный интервал или используется общий. За проход обновляются до пяти ранее принятых товаров на источник, первыми идут те, которые дольше ждали. Реальное время зависит от очереди и ответа площадки. Отдельно запущенное фоновое ядро считается работающей системой. «Запустить сейчас» запускает повторную попытку включённых источников, включая источники с паузой после ошибки. Фоновое расписание учитывает эту паузу.

## Диагностика запуска из приложения, 14.11.2026

Подтверждена ошибка интеграции на Windows. Ядро читает канал stdin, связанный с окном приложения. Автосбор наследовал этот занятый канал. Изолированный запуск прежним способом завис до вывода журнала. С stdin=subprocess.DEVNULL тот же процесс завершился успешно. Ошибка воспроизведена без сетевых запросов. Поэтому прежние проверки запуска из консоли не подтверждали запуск из настольного приложения.

В r52/core/autocollect.py исправлен входной канал subprocess. При ошибке worker.log сохраняется в logs/collect-*.log до очистки временного каталога. Явный ручной запуск теперь учитывает force и выполняет повторную попытку во время retry_after.

Команда python -B -m unittest discover -s tests -p test_autocollect.py -v завершилась успешно, 6 тестов. Новый тест проверяет запуск через python.exe и pythonw.exe при открытом канале stdin настольного приложения. Несуществующий тестовый источник обеспечивает завершение до сетевых запросов. Отдельно проверены сохранение журнала и ручная повторная попытка.

Файлы r52/collectors/*.py в ходе этой диагностики не изменены, подтверждено SHA-256. Параметр use_proxies=True установлен ранее. В используемой папке данных LOCALAPPDATA/R52 отсутствует collectors/proxies.json, поэтому пул использует прямое соединение. Включение параметра само по себе не подтверждает использование прокси. Некоторые собственные HTTP/браузерные пути сборщиков также не передают настройки пула.

После изменения core/autocollect.py требуется перезапуск ядра. Live-успех после исправления ещё не проверен. Поисковые цели в рабочей базе на момент проверки отсутствовали. Исходные исторические результаты выше сохранены.

## Диагностика пустых результатов, 14.11.2026

Журнал каждого запуска сохраняется в LOCALAPPDATA/R52/logs/collect-*.log, включая штатное завершение с нулём наблюдений. В core.log записываются источник, режим, число переданных, отклонённых и известных карточек и имя журнала. Отказ при публикации содержит файл экспорта, причину и traceback.

В обвязке auto_worker добавлены этапы initialize, collect_product_start/return, search_start/discover_links_start, write_start/complete и close_start/complete. Записываются ID карточки, статус ответа, статистика пула прокси и сборщика. При NO_RESULT/FAILED/BLOCKED журнал указывает оставшиеся непроверенные ID. Исключения сохраняют traceback. Каждые 60 секунд активного процесса faulthandler записывает стеки потоков. Это диагностический снимок длительного ожидания, сам по себе он не означает сбой.

Девять адресных офлайн-тестов прошли. Проверены пустой результат с успешным завершением процесса, идентификация текущей и непроверенных карточек, сохранение traceback, предыдущие проверки запуска и импорта. Сетевые запросы в тестах отсутствуют. Файлы wb.py, ozon.py, avito.py, farpost.py, aliexpress.py, base.py, proxy_pool.py и pw_fetch.py совпадают с резервными копиями по SHA-256.

Для загрузки обновлённой обвязки ядра требуется полный перезапуск R-52. Старые удалённые журналы Ozon восстановить этой доработкой нельзя. Конкретная причина внутри сборщика видна в следующем запуске настолько, насколько её раскрывают сообщения сборщика и стеки выполнения.

## Широкий поиск, 14.11.2026

Добавлена только миграция v10, прежние v1-v9 сохранены. Существующие цели имеют origin=USER, автоматические origin=CATALOG. По умолчанию autocollect.broad_search=true. Подготовлены 16 тематик для каждого из шести источников. Совпавшие существующие ручные цели сохраняют настройки. Добавление ручной цели с текстом автоматической переводит её под управление пользователя.

За цикл выбирается следующая автоматическая тематика каждого доступного источника, до пяти карточек на неё и в пределах существующего общего лимита новых предложений. Интервал поиска задаёт минимальную паузу между автоматическими тематиками одного источника. Ручной запуск выполняет очередной проход сразу. После успешной или содержащей известные товары страницы её номер увеличивается. Пустой результат сбрасывает страницу этой тематики на первую, следующая тематика выбирается по времени предыдущего запуска. Прогресс хранится в общей базе. При исчерпании общего лимита первыми в следующих проходах становятся ожидающие источники.

Широкий поиск использует существующий collect_by_search, формат экспорта, FolderWatcher и импорт. Найденные новые предложения принимаются через прежний конвейер. Это постепенный обход выдачи выбранных тематик, полнота всего ассортимента маркетплейсов не гарантирована. Набор тематик выбран при реализации и доступен в интерфейсе для просмотра. Доступность площадки и качество её текущего сборщика определяют фактический результат.

Проверено 13 тестов автосбора, 13 API и 17 базовых тестов. Проверены сохранение товара через конвейер, отсутствие ручных целей, чередование категорий, страницы после перезапуска, интервал, выключение режима, общий лимит, смена источников, перенос ручного управления и миграция старых целей. Проверка JavaScript node --check прошла. Миграция на копии рабочей базы в памяти сохранила 24 товара и 48 наблюдений, создала 96 автоматических целей. Рабочая база этой проверкой не изменялась. Все r52/collectors/*.py совпадают с резервными копиями по SHA-256.

Для применения нужен полный перезапуск R-52. Штатная миграция перед обновлением существующей базы создаёт резервную копию. Live-обход новых автоматических тематик и визуальная проверка обновлённого экрана в этой итерации не проводились.
